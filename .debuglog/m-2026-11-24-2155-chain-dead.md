# Measurement: "the hook chain is dead" - WITHDRAWN, it was my own instrument

**Taken:** 2026-11-24 21:51-22:05 (Asia/Shanghai).
**By:** the agent that took over the handoff.
**Status:** **the hypothesis is withdrawn.** It was an artefact of a broken
probe, not a fact about the machine. The original 20:43 evidence stands
exactly as the handoff described it.

## What was claimed

At 21:55 this agent wrote that the low-level hook chain was dead
machine-wide, because:

- `.cache/hook-probe2.ps1` (rebuilt) had been alive since 21:33 with its
  hook installed (`RE-ARM ok` every 10 s, heartbeat every second) and had
  logged **zero** events;
- `.cache/hook-probe3.ps1` (the original lineage, one compile error fixed)
  had been alive since 21:53 with `hook installed hwnd=0x2F501D7` and had
  logged **zero** events;
- the previous probe (`.cache/hook-probe.log`) had logged 2445 rows until
  **21:01:45** and then stopped, its process gone.

## What killed the hypothesis

A **stand-alone native probe** - `hookprobe.exe`, compiled with the .NET
Framework compiler, no PowerShell, no `Add-Type`, no runtime hosting -
caught events immediately:

```
22:02:53.628 | down vk=13 (0x0D) scan=0x1C flags=0x0 extra=- | front=6380:fix pKO | focus=6380:
22:02:53.724 | up   vk=13 (0x0D) scan=0x1C flags=0x80 extra=- | front=6380:fix pKO | focus=6380:
```

**The chain was alive all along.** The PowerShell-hosted probes were the
broken instrument.

Then the native probe itself fell silent after exactly one event - because
*it* did its file I/O inside the hook callback, the same mistake as the
original. **Windows removes a low-level hook whose callback misses
`LowLevelHooksTimeout`.** That is almost certainly what happened to the
original probe at 21:01:45: its callback opened a `StreamWriter`, wrote and
flushed **on the hook thread**, and one slow write was enough for Windows to
remove the hook. The log stops, the process lingers, and every other hook on
the machine looks fine - because the *chain* is fine and only that one hook
was removed.

`.cache/hookprobe2.exe` is the corrected instrument: the callback copies 24
bytes into a fixed ring buffer and returns; a background thread does every
bit of the formatting and the file I/O.

## Why this matters for the original bug

The 20:43 evidence is unaffected - it came from `hook-probe.log`, which
demonstrably worked for 39 minutes and logged thousands of rows, including
the owner's typing at 20:43:40-42 and the Chrome chord at 20:43:29. Its
27-second hole at 20:43:01.914-20:43:29.178 is **not** an artefact of a
removed hook: the same hook logged rows on both sides of the hole, and a
removed hook never comes back on its own.

**So the original puzzle stands as written:** a physical Ctrl+T in the
Project KO terminal reached the web view, and no low-level hook on the
machine was called for it - while eleven seconds later the same chord in
Chrome reached both Toxic's hook and the stand-alone probe.

## The lesson, written down

| Rule | Why |
| --- | --- |
| **Never do I/O in a low-level hook callback** | Windows removes the hook when the callback misses `LowLevelHooksTimeout`; the failure looks exactly like "the chain is broken" |
| **Log a heartbeat that is not produced by the hook** | otherwise "no events" is indistinguishable from "the hook was removed" |
| **Prove an instrument against an independent one** | two probes sharing a hosting model share a failure mode - the PowerShell probes agreed with each other and were both wrong |
| **A hookless `GetAsyncKeyState` poller is the control** | it reads the global key state without the chain, so it separates "the chain is cut" from "the keys are not entering the system" |
