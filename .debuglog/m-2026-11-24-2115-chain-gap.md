# Measurement: the chain saw no keyboard event at all while Project KO was in front

**Taken:** 2026-11-24 21:15 (Asia/Shanghai), re-reading `.cache/hook-probe.log`
raw, without the previous agent's summary.
**By:** the agent that took over the handoff.

## Why this re-read

The handoff and `ruled-out.md` both say the stand-alone probe "logged **zero
rows whose foreground is `18776`**" during the 20:43 test. That phrasing
leaves room for rows logged against some *other* window during the same
seconds. If such rows existed, the fault would be "the key went somewhere
else". If they do not exist, the fault is something else entirely.

## What the raw log says

Rows in `.cache/hook-probe.log` around the test:

```
20:43:00.242 | down vk=164 (0xA4) scan=0x38 flags=0x20 extra=- | front=41368:MiniMax Code
20:43:00.737 | down vk=9   (0x09) scan=0x0F flags=0x20 extra=- | front=41368:MiniMax Code
20:43:01.530 | down vk=9   (0x09) scan=0x0F flags=0x20 extra=- | front=3792:Task Switching
20:43:01.914 | up   vk=164 (0xA4) scan=0x38 flags=0x80 extra=- | front=3792:Task Switching
                                     <-- 27.3 seconds with no row of any kind
20:43:29.178 | down vk=162 (0xA2) scan=0x1D flags=0x0  extra=- | front=11028:YouTube - Google Chrome
20:43:29.180 | down vk=84  (0x54) scan=0x14 flags=0x0  extra=- | front=11028:YouTube - Google Chrome
```

**There is not a single row between 20:43:01.914 and 20:43:29.178** - no
`Ctrl`, no `T`, no character, no mouse-ish noise, nothing. The hole is
27.3 seconds long and it opens exactly when the foreground sampler says
Project KO came to the front (20:43:01.987) and closes exactly when Chrome
came to the front (20:43:26.499) plus the owner's first Chrome chord.

Meanwhile the Project KO web-view probe recorded two **complete** Ctrl+T
presses inside that hole (20:43:14.828->15.451 and 20:43:18.159->18.273,
`ctrl=1 shift=0 alt=0`).

## Why the hole is not a broken instrument

The probe was one single session: `=== probe started 2026-11-24
20:22:23.119 pid=18144 ===` and one `hook installed hwnd=0x33C40C39`. The
script installs the hook **once** (`.cache/hook-probe.ps1`, `SetWindowsHookExW`
inside `HookProbe.Run`) and never re-arms it, so a Windows removal would be
**permanent** - the log would simply stop. It did not: rows resume at
20:43:29.178 and continue to 21:01:45. The hook was therefore alive on both
sides of the hole.

(The script does do its file I/O *inside* the hook callback, which is what
makes a hook vulnerable to `LowLevelHooksTimeout` removal. That is a real
flaw, and it is what the rebuilt probe fixes - but it cannot explain a hole
that has rows after it.)

## Verdict

**This corrects the handoff's central claim.** The fault is not "the
`WH_KEYBOARD_LL` chain is cut for the Project KO window". It is:

> While the Project KO window was in front, **no keyboard event of any kind
> entered the system input path** - and yet the Project KO web view received
> two complete Ctrl+T key sequences.

Combined with the integrity measurement
([m-2026-11-24-2113-token-integrity-levels.md](m-2026-11-24-2113-token-integrity-levels.md)),
in which every process involved is Medium, this means:

**The Ctrl+T that the web view saw was not produced by a physical keystroke.**
A physical keystroke aimed at a Medium-integrity window always produces a
low-level hook callback; none happened. The key event was produced *inside*
the application - by a posted message, a protocol-driven input (CDP / raw
input), or a synthesised DOM event.

That kills the candidate list in handoff section 5, every entry of which
assumed "the key came from the keyboard but bypassed the hook chain". The
question changes from *what delivers a key to PKO without the chain* to
**what produces a key event inside the Project KO web view**.

## The instrument is now dead

`.cache/hook-probe.log` stops at **21:01:45** and no process with
`hook-probe` in its command line exists any more. The only witness to the
cut is gone, and the rebuilt probe (`.cache/hook-probe2.ps1`, heartbeat +
re-arm + focused window + no I/O in the callback) exists to replace it.
